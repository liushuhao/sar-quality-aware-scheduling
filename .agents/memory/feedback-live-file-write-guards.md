对**可能被别的进程写**的文件（remember store 的 `core-memories.md`、插件/外部工具维护的配置）做读-改-写时，
必须显式设计并发语义；默认按"这个文件归我独占"来写是错的。

**Why：** 2026-10-01 给 `.remember` 写 GC 工具，三轮独立复核挖出四个同源缺陷：
1. **守卫放在耗时步骤之前**：源文件校验通过后，还要按体积写入（61 MB 备份 + fsync）才 `os.replace`，
   这段就是窗口——并发追加落进去被静默覆盖，**退出码还是 0**（丢数据还报成功）。
2. **守卫自己就是窗口**：把守卫挪进写入计划后仍在 stage 之前，而守卫里的 `sha256_file` 本身是 O(size)
   （61 MB 约 200 ms），复核方在同一时点仍能复现丢失。修法必须把窗口降到**不可约**（改成 O(1) 的
   `stat`：size + mtime_ns；完整 hash 只在快照时取一次锁定身份），而不是换个位置。
3. **read-back 失败时回滚销毁并发写**：写入后比对发现不一致（说明有人在这之后写了），却拿运行前的备份
   盖回去——报"干净回滚"的同时删掉了对方内容。正确做法是**原地保留、明确报告**，不动任何文件。
4. **失败路径的承诺没兑现**：回滚逻辑打印"备份已保留供手工恢复"，紧接着的删除循环把备份删了——
   错误处理本身成了数据丢失源。

**How to apply：**
- 先 **stage**（写 pid 临时件 + fsync）再 **commit**；无守卫窗口不得随文件体积增长。
- 守卫紧贴 `os.replace`，且只用 O(1) 检查（size + mtime_ns）——检查本身耗时就是窗口。
- 写入后 read-back 逐字节比对；不一致 = 有并发写 → **原地保留**，报告状态，不回滚。
- 回滚只在"源未生效 或 已从备份成功恢复"时才删备份；恢复失败必须留备份并说明。
- 残余窗口（stat 与 replace 之间的微秒级）写进文档，禁宣称"零丢失"；要归零得上文件锁，属另一个决定。
- 验证方式：大文件 + 定时追加 marker，多时点多次复跑（本轮 61 MB × 20 次、审方独立 12 次，0 丢失才算过）。

见 feedback-atomic-progress-write-and-resume-fallback（运行产物的原子写）、[[feedback-assert-silent-skip]]（守卫的判别力）。

**追加（2026-10-01 第二段实证：给记忆库加文件锁）**：对活文件做**原地改写**时，"锁住下一次追加的落点"
是不够的——`ftruncate` 会改变 EOF，追加随后落进文件体内，落在锁区之外。首版据此只锁 `[old_size, old_size+4096)`，
独立复核实测「**锁从未挡住任何追加**」，而事件时序上仍能观察到 marker 存活，于是给出假信心。
正解：**锁 `[0, size+4096)`**（整个文件 + 下一次追加落点），且**解锁必须用同一区间**（Windows 上区间不等则解锁失败，
只能靠关句柄兜底）。实测该区间下：truncate 前 / 后 / 写到一半的追加**全部 Permission denied**，解锁后正常。
同段另两条：
- **测试要断言机制本身跑过**，不只断言结果。racetest 只记"追加的 marker 是否存活"，而 blocked 分支**从未触发**——
  机制没生效也照样"全绿"。补法：至少一例直接断言机制的确证（这里是 appender 拿到 `PermissionError`）。
- **错误路径的文案必须绑定"失败的那次 run"**。恢复配方默认用了当前 tag 的 `.bak`，但死掉的是上一次 run：
  配方指向不存在的文件，且没列出会阻塞重跑的侧件（rc 6）。凡是错误路径里出现的标识符，逐个问"这是本次还是上次"。
